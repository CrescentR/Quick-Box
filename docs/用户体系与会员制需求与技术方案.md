# QuickBox 用户体系与会员制需求与技术方案

## 1. 需求分析

### 1.1 背景

远程插件市场会自然引入用户状态：

- 用户需要登录后下载插件。
- 部分插件可能需要会员权益。
- 后续可能需要同步插件安装记录、购买记录、设备授权和会员状态。
- AI、OCR、PDF、数据库等重型或高价值插件可能成为会员权益的一部分。

因此，用户体系不是独立功能，而是插件市场、会员制和后续云能力的基础。

### 1.2 用户目标

用户需要：

- 查看当前是否登录。
- 登录和退出登录。
- 查看会员状态。
- 查看会员到期时间。
- 查看自己可用的插件权益。
- 在插件详情页知道是否有下载权限。
- 在未登录或权益不足时得到明确引导。

### 1.3 产品原则

1. 不强制登录才能使用内置工具。
2. 登录只影响远程能力：插件下载、会员插件、云同步、未来 AI 服务。
3. 用户状态必须在桌面端可离线展示缓存。
4. 权益校验失败时不能破坏已安装的本地插件使用体验。
5. 会员制第一版先做状态与权益，不急于做完整支付闭环。

## 2. PRD

### 2.1 页面结构

新增账户页：

- 未登录状态
  - 登录入口
  - 说明登录用途
  - 隐私说明
- 已登录状态
  - 用户昵称
  - 邮箱或用户 ID
  - 会员状态
  - 到期时间
  - 权益列表
  - 退出登录
  - 刷新状态

### 2.2 登录状态

状态：

- 未登录
- 登录中
- 已登录
- 登录过期
- 网络错误
- 权益刷新失败

### 2.3 会员状态

状态：

- 非会员
- 会员有效
- 会员即将到期
- 会员已过期
- 权益未知

### 2.4 权益模型

权益不应只用一个 `isVip` 判断。建议用 entitlement 列表：

- `plugin.ocr.rapidocr`
- `plugin.ai.assistant`
- `market.download.member`
- `cloud.sync`

插件详情页根据 `requiredEntitlements` 判断用户是否可下载。

### 2.5 插件市场联动

插件详情页操作逻辑：

- 未登录 + 需要登录：显示登录。
- 已登录 + 免费插件：允许下载。
- 已登录 + 会员插件 + 有权益：允许下载。
- 已登录 + 会员插件 + 无权益：显示开通会员。
- 网络不可用：显示上次缓存权益，但新下载需要重新校验。

### 2.6 非功能需求

- 账户页打开要快。
- Token 过期要能刷新。
- 登录失败要有明确错误。
- 不要因为账户接口失败影响本地工具启动。
- 会员状态必须展示更新时间，避免用户误判。

## 3. 技术分析

### 3.1 API 设计

建议接口：

```text
POST /api/auth/login
POST /api/auth/logout
POST /api/auth/refresh
GET /api/account/me
GET /api/account/entitlements
```

登录方式待确认。当前可设计接口层，不写死 UI：

- 邮箱密码
- 邮箱验证码
- 浏览器 OAuth
- 手动 token

### 3.2 前端模块

建议新增：

```text
src/pages/AccountPage.tsx
src/api/account-api.ts
src/stores/account-store.ts
src/core/account/account-types.ts
```

### 3.3 后端模块

建议新增：

```text
src-tauri/src/commands/account.rs
src-tauri/src/storage/account_store.rs
```

### 3.4 本地存储

建议 SQLite 表：

```text
account_session
account_entitlements_cache
```

`account_session`：

- `user_id`
- `display_name`
- `email`
- `access_token`
- `refresh_token`
- `expires_at`
- `updated_at`

`account_entitlements_cache`：

- `user_id`
- `entitlements_json`
- `membership_json`
- `updated_at`

正式版应评估系统密钥链存储 token。第一版如果先用 SQLite，需要在文档和代码里明确风险边界。

### 3.5 与插件市场关系

账户模块提供：

- 当前用户
- 登录状态
- 会员状态
- 权益集合

插件市场消费：

- 下载前检查登录。
- 下载前检查会员权益。
- 插件卡片展示免费 / 会员。
- 插件详情展示可用 / 不可用。

## 4. 开发计划

### 4.1 第一阶段：账户状态骨架

1. 新增账户类型。
2. 新增账户 store。
3. 新增账户 API 封装。
4. 新增账户页面。
5. 插件市场顶部展示登录状态。

### 4.2 第二阶段：真实登录

1. 确认登录方式。
2. 接入登录接口。
3. 存储 session。
4. 支持刷新 token。
5. 支持退出登录。

### 4.3 第三阶段：会员权益

1. 拉取权益。
2. 缓存权益。
3. 插件市场联动权益。
4. 下载前校验权益。
5. 权益过期提示。

## 5. 需要确认的问题

1. 第一版登录方式是什么？
2. 是否已有后端服务，还是需要先设计 mock API？
3. 会员是否按月/年订阅，还是一次性买断某些插件？
4. 免费插件是否允许未登录下载？
5. Token 是否允许第一版存在 SQLite，还是必须接系统密钥链？
6. 是否需要设备数量限制？

## 6. 当前建议

建议先做账户状态骨架和插件市场联动：

- 账户页先支持 mock 登录状态。
- 插件市场接口按远程真实形状设计。
- 下载会员插件时走权益判断流程。
- 等后端登录方式确认后，再接真实接口。

这样不会阻塞插件市场页面开发，也不会把登录方式过早写死。
