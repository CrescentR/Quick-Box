# QuickBox 插件市场需求与技术方案

## 1. 需求分析

### 1.1 背景

QuickBox 当前已经具备插件化基础：

- 所有工具通过 `ToolPlugin` 注册。
- 启动器命令来自 `PluginRegistry`。
- 插件启用状态已经持久化到 SQLite。
- 插件权限通过 metadata 显式声明。
- 当前插件管理页只能展示和启停已注册的官方内置插件。

`docs/V0.5.md` 对后续产品方向给出了明确判断：

- 主程序只内置高频、轻量、无依赖工具。
- OCR、AI、PDF、数据库客户端、Docker 管理等重型能力应做成可选插件。
- 插件市场需要展示插件体积、是否离线、是否需要网络、是否需要系统权限、是否包含模型、是否需要额外配置。
- OCR 应作为可选大型插件，不应随主程序内置模型或 ONNX Runtime。

因此，插件市场的核心目的不是把更多工具硬塞进主程序，而是让 QuickBox 从“工具合集”走向“平台”：主程序保持轻，重型能力按需安装、按需启用。

### 1.2 当前能力边界

当前项目已有：

- `PluginSource = 'builtin' | 'local' | 'market'`
- 插件启停状态存储表 `plugins`
- 插件管理页面
- Tauri command 封装
- SQLite 存储
- 权限类型声明

当前项目缺少：

- 插件市场清单数据模型
- 市场列表页
- 市场插件详情页
- 插件安装状态
- 插件包下载流程
- 插件包校验流程
- 插件包解压流程
- 外部插件加载流程
- 插件签名校验
- 插件运行时隔离
- 插件资源目录规范

### 1.3 用户目标

用户打开插件市场后，应能快速判断一个插件是否适合安装：

- 它解决什么问题。
- 它属于轻量插件、普通插件还是大型插件。
- 它有多大。
- 它是否离线可用。
- 它是否需要网络。
- 它需要哪些系统权限。
- 它是否包含模型或原生运行时。
- 它是否需要额外配置。
- 它是否已经安装。
- 安装后是否可以启用、停用和卸载。

### 1.4 产品原则

1. 主程序保持轻量。
2. 插件市场先解决“发现、判断、安装状态管理”，再扩展真实下载与外部加载。
3. 大型插件必须把依赖、模型、权限和体积标清楚。
4. OCR 插件不内置到主程序；市场只负责展示和安装入口。
5. 没有签名校验和加载隔离前，不执行来自网络的任意前端代码。
6. 插件市场的 UI 应该是工具型界面，强调扫描、筛选、比较和状态，不做营销页。

## 2. PRD

### 2.1 功能范围

第一阶段目标：实现插件市场基础体验。

包含：

- 插件市场页面。
- 市场插件列表。
- 插件分类筛选。
- 插件搜索。
- 插件详情信息。
- 插件安装状态展示。
- 插件安装、卸载、启用、停用入口。
- OCR 插件市场条目。
- 插件市场元数据本地持久化。

暂不包含：

- 在线账号体系。
- 开发者上传平台。
- 云端支付。
- 插件评分评论。
- 任意第三方插件代码执行。
- 自动更新。
- 插件签名体系的完整落地。

### 2.2 页面结构

插件管理页应升级为“已安装 + 市场”一体页面，或新增独立“插件市场”Tab。

建议结构：

- 顶部统计区
  - 已安装插件数
  - 可安装插件数
  - 已启用插件数
  - 大型插件数
- 筛选区
  - 全部
  - 开发者基础包
  - 前端增强包
  - 后端增强包
  - 运维排查包
  - 图片处理包
  - OCR 识别包
  - AI 效率包
- 搜索区
  - 按插件名称、描述、关键词搜索
- 插件列表
  - 插件名称
  - 简短描述
  - 分类
  - 体积
  - 离线能力
  - 网络需求
  - 权限摘要
  - 模型标记
  - 配置标记
  - 安装状态
- 插件详情
  - 完整描述
  - 运行方式
  - 依赖说明
  - 权限说明
  - 安装内容结构
  - 风险提示
  - 操作按钮

### 2.3 插件状态

市场插件需要区分以下状态：

- 未安装
- 已安装
- 已启用
- 已停用
- 安装失败
- 需要配置
- 资源缺失

OCR 插件在第一阶段可以显示为：

- 未安装：只展示市场信息。
- 已安装但资源缺失：插件目录存在，但缺少 `rapidocr.exe`、`onnxruntime.dll` 或模型文件。
- 需要配置：用户需要选择或确认插件资源目录。
- 已启用：资源检查通过，并出现在启动器命令中。

### 2.4 OCR 插件条目

OCR 插件市场展示信息：

- 名称：OCR 图片转文字
- 分类：OCR 识别包
- 推荐内置：否
- 体积：50~120MB
- 运行方式：本地离线
- 网络需求：否
- 系统权限：读文件
- 原生依赖：ONNX Runtime
- 模型：包含模型
- 支持语言：中文 / 英文 / 日文
- 额外配置：可能需要选择插件资源目录

OCR 插件包结构按 `docs/V0.5.md`：

```text
ocr-plugin.zip
├─ plugin.json
├─ frontend/
├─ native/
│  ├─ rapidocr.exe
│  └─ onnxruntime.dll
└─ models/
   ├─ det.onnx
   ├─ rec.onnx
   └─ cls.onnx
```

### 2.5 用户流程

#### 2.5.1 浏览市场

1. 用户进入插件市场。
2. 查看插件列表。
3. 通过分类或搜索定位插件。
4. 点击插件查看详情。

#### 2.5.2 安装 OCR 插件

1. 用户打开 OCR 插件详情。
2. 查看体积、依赖、权限和模型说明。
3. 点击安装。
4. 系统检查插件资源目录。
5. 如果资源缺失，提示用户补齐插件包内容。
6. 资源检查通过后，插件状态变为已安装。
7. 用户启用插件。
8. 启动器出现 OCR 相关命令。

#### 2.5.3 卸载插件

1. 用户在插件详情点击卸载。
2. 系统移除安装状态。
3. 是否删除本地资源目录需要确认后再落地。

### 2.6 非功能需求

- 插件市场页面首次打开应快速渲染。
- 市场清单可本地缓存。
- 插件状态必须持久化。
- 大型插件不得阻塞主线程。
- 插件权限必须可见。
- 插件安装失败必须有可读错误信息。
- 没有校验机制前，不自动执行外部插件代码。

## 3. 技术分析

### 3.1 数据模型

市场插件需要独立于当前 `ToolPlugin`。原因：

- `ToolPlugin` 表示已经可注册、可执行的插件。
- 市场条目表示可发现、可安装、可能尚不可执行的插件。
- OCR 这类插件需要展示安装包、模型、原生依赖、运行方式和资源检查信息，这些不是当前 `ToolPlugin` 的字段。

建议新增市场条目模型，字段在确认后再落地为 TypeScript 与 Rust 类型：

- 插件 ID
- 名称
- 版本
- 描述
- 作者
- 分类
- 标签
- 体积
- 离线能力
- 网络需求
- 权限列表
- 是否包含模型
- 是否需要配置
- 运行方式
- 依赖列表
- 支持平台
- 安装包结构说明
- 安装状态

### 3.2 存储设计

建议新增 SQLite 表：

- `plugin_market_items`
  - 存储市场清单缓存。
- `plugin_installations`
  - 存储市场插件安装状态、启用状态、资源目录、错误信息。

当前已有 `plugins` 表可继续保存已注册插件启用状态，但市场插件安装状态不应强塞进现有 `plugins.metadata`，否则后续升级、卸载和资源检查会变得混乱。

### 3.3 前端结构

建议新增：

```text
src/pages/PluginMarketPage.tsx
src/api/plugin-market-api.ts
src/core/plugin-market/plugin-market-types.ts
src/core/plugin-market/default-market-items.ts
```

如果选择在现有插件管理页中做 Tab，则可以复用：

```text
src/pages/PluginManagerPage.tsx
```

但从产品边界看，插件管理和插件市场是两个不同任务：

- 插件管理：处理已安装插件。
- 插件市场：发现和安装插件。

所以更建议新增页面或在 `PluginManagerPage` 内部建立清晰的 Tab 结构。

### 3.4 后端结构

建议新增：

```text
src-tauri/src/commands/plugin_market.rs
src-tauri/src/storage/plugin_market_store.rs
```

命令职责：

- 加载市场清单。
- 加载安装状态。
- 安装插件。
- 卸载插件。
- 启用或停用市场插件。
- 检查插件资源完整性。

第一阶段安装动作可以只写入安装状态和资源目录，不做网络下载。真实下载、解压、签名校验应在确认后进入第二阶段。

### 3.5 OCR 运行设计

OCR 插件推荐运行方式：

```text
QuickBox UI
↓
Tauri command
↓
检查插件资源目录
↓
调用 native/rapidocr.exe
↓
读取 models/
↓
返回识别文本
```

主程序不内置：

- `rapidocr.exe`
- `onnxruntime.dll`
- `det.onnx`
- `rec.onnx`
- `cls.onnx`

主程序只负责：

- 展示 OCR 插件市场条目。
- 管理安装状态。
- 校验资源目录。
- 在插件启用后提供调用入口。

### 3.6 安全边界

第一阶段必须避免：

- 从网络下载后直接执行插件代码。
- 动态加载未校验的前端 JS。
- 默认赋予大型插件文件写入、进程执行等高风险权限。

第一阶段可以做：

- 本地市场清单。
- 安装状态管理。
- 资源完整性检查。
- 大型插件权限展示。
- OCR 插件资源目录检查。

第二阶段再做：

- 插件包下载。
- Hash 校验。
- 签名校验。
- 解压安装。
- 外部插件加载。
- 插件更新。

### 3.7 与当前架构的关系

当前架构中的 `ToolPlugin` 和 `PluginRegistry` 仍然保留，只管理已经能运行的插件。

插件市场新增一层：

```text
MarketPluginItem
↓ 安装
PluginInstallation
↓ 资源检查通过
ToolPlugin 注册或启用
```

由于当前项目尚未支持外部 React 视图动态加载，第一阶段不应承诺“安装后立即运行任意第三方前端插件”。对于 OCR，可以先通过主程序内置一个受控的 OCR 视图壳，真正的大型资源放在插件目录。

## 4. 开发计划

### 4.1 第一阶段：插件市场基础版

1. 新增插件市场文档。
2. 新增市场条目类型。
3. 新增本地市场清单。
4. 新增市场状态存储。
5. 新增插件市场 API。
6. 新增插件市场页面或插件管理页 Tab。
7. 展示 OCR 插件条目。
8. 支持安装状态、启用状态和卸载状态。
9. 支持资源目录检查。
10. 完成类型检查、构建和页面验证。

### 4.2 第二阶段：OCR 插件资源接入

1. 确认 OCR 插件资源目录。
2. 确认 `rapidocr.exe` 命令行参数。
3. 确认识别结果输出格式。
4. 新增 OCR Tauri command。
5. 新增 OCR 视图壳。
6. 支持图片选择。
7. 调用 RapidOCR。
8. 展示识别结果。

### 4.3 第三阶段：插件包安装

1. 下载插件包。
2. 校验 Hash。
3. 解压插件包。
4. 校验目录结构。
5. 写入安装状态。
6. 提供更新和卸载。

## 5. 需要确认的问题

以下问题无法从现有代码和文档中得到精确答案，需要开发前确认：

1. 插件市场第一阶段是否允许使用“本地内置市场清单”，暂不接入远程市场接口？
2. OCR 插件第一阶段是否只做市场展示、安装状态和资源目录检查，暂不实现真实 OCR 识别？
3. 如果要实现真实 OCR 识别，请提供 `rapidocr.exe` 的命令行调用方式、参数格式和输出格式。
4. 插件安装资源目录是否使用 QuickBox app data 目录，还是允许用户自定义目录？
5. 卸载插件时，是否删除插件资源文件，还是只删除安装状态？
6. 插件市场是否需要独立页面，还是合并进当前插件管理页并使用 Tab？
7. 市场清单字段确认后，是否需要兼容未来远程 JSON 清单？

## 6. 建议结论

建议先实现第一阶段：

- 使用本地内置市场清单。
- 将插件市场做成插件管理页里的独立 Tab，减少导航改造。
- OCR 先作为大型插件条目出现。
- 安装动作先记录安装状态和资源目录。
- 资源检查只验证目录结构和关键文件是否存在。
- 不执行外部插件代码。
- 不下载网络资源。

这样可以先把产品骨架和安全边界立住，再逐步接入真实下载、签名校验和 OCR 运行能力。
