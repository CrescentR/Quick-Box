# QuickBox 产品与 UI 重构开发文档 V0.1

> 目的：在继续开发前，先明确 QuickBox 的产品气质、页面结构、视觉方向、组件边界、阶段计划与验收标准。  
> 适用范围：当前 Tauri 2 + React + TypeScript + Rust 项目。  
> 与现有文档关系：本文件补充并约束 `docs/quickbox_ui_design_system.md`，更偏产品落地与开发执行。

---

## 1. 当前问题诊断

当前项目已经具备基础能力，但整体仍然不像一个正式桌面产品，主要问题不是“少几个组件”，而是以下几类结构性问题：

### 1.1 视觉语言不统一

- Launcher、工具页、设置页、插件页不是同一种产品气质。
- 组件层已经开始建立，但页面层仍然像“拼接 demo”。
- 标题、信息卡片、列表区、详情区缺乏稳定的层级系统。
- 页面里虽然用了暗色和 accent，但没有形成清晰的视觉重心。

### 1.2 页面缺乏产品感

- 页面布局更像内部管理工具，而不是桌面启动器。
- “内容区 + 卡片 + 标签”使用过多，但缺少真正的页面叙事。
- 右侧详情区目前只是堆信息，不像“命令详情 / 工具预览 / 执行动作面板”。
- 设置页和插件页虽然不再是空白，但仍然缺少正式产品的目的性与结构节奏。

### 1.3 信息密度和优先级失衡

- 列表区信息太散，不够利落。
- 详情区信息太平均，没有主次。
- 统计、标签、说明文字、快捷键提示同时出现时，缺少明确的阅读路径。
- 页面中很多元素是“有了”，但不是“恰到好处”。

### 1.4 工程层仍存在“两套 UI 并存”风险

- 设计系统组件在 `src/ui/`，但历史样式和旧页面模式仍有残留。
- 页面开发目前还是偏“边做边试”，缺少稳定的页面规范和阶段性目标。
- 如果不先统一产品文档，后续越开发越容易继续分叉。

---

## 2. 产品目标重述

QuickBox 不是管理后台，不是 IDE，不是设置中心，也不是插件市场首页。  
它的核心身份是：

> 一个高频呼出、快速筛选、快速执行、快速关闭的桌面工具入口。

因此 UI 的第一原则不是“功能很多”，而是：

- 一眼知道当前能做什么
- 键盘操作时没有视觉噪音
- 页面切换时仍然像同一个产品
- 工具视图打开后不像跳到另一套系统

---

## 3. 目标气质

QuickBox 的目标气质不是炫技，不是“赛博玻璃壳”，也不是“普通后台暗色主题”。

### 3.1 关键词

- Quiet precision
- Desktop-native
- Keyboard-first
- Developer-focused
- Confident but restrained

### 3.2 应有观感

- 更像 Raycast / Linear / Arc / Windows Fluent 的交集
- 背景有材质感，但阅读区域必须稳定
- 有重点高亮，但不允许全屏都在发光
- 有卡片层级，但不能页面里到处是边框盒子
- 让用户感觉“这是一个真正会继续长大的产品”

### 3.3 明确不要的方向

- 不要“后台管理系统暗黑皮肤”
- 不要“到处都是圆角卡片堆叠”
- 不要“每个区块都同等重要”
- 不要“紫色能量条 + 大片渐变 + 缺乏内容逻辑”
- 不要“像练手项目的样子”

---

## 4. 产品信息架构

QuickBox V0.1 只保留三个一级页面：

1. Launcher
2. Plugins
3. Settings

这是完整产品的最小闭环。

### 4.1 Launcher

职责：

- 输入查询
- 浏览命令
- 打开工具视图
- 查看命令详情
- 接受键盘操作

Launcher 是主入口，视觉优先级最高。

### 4.2 Plugins

职责：

- 展示官方内置工具
- 展示权限与命令数量
- 展示启用状态
- 为未来本地插件 / 市场插件预留结构

Plugins 页不应做成“市场首页”，而应做成“能力管理页”。

### 4.3 Settings

职责：

- 管理主题
- 管理热键
- 管理桌面集成
- 承载未来更多基础配置

Settings 不应做成“系统设置大杂烩”，而应保持轻量。

## 5. 页面级设计规范

## 5.1 Launcher 页面

### 5.1.1 页面目标

Launcher 页面必须像一个桌面启动器，而不是“搜索列表 + 信息卡片”。

### 5.1.2 推荐结构

```text
┌ Window Header / Brand / Nav ───────────────────────────────┐
│ QuickBox | Current page | minimal meta                     │
├ Search Bar ────────────────────────────────────────────────┤
│ Input + loading + subtle hint                              │
├ Main Content ──────────────────────────────────────────────┤
│ Left: Command List (380px) | Right: Detail / Tool View     │
├ Footer ────────────────────────────────────────────────────┤
│ Shortcuts / result count / context hints                   │
└─────────────────────────────────────────────────────────────┘
```

### 5.1.3 左侧列表规则

- 列表项必须利落，信息最多两层。
- 标题优先，副标题为补充，不要过长。
- 标签只保留一到两个关键标签。
- 选中态必须非常明确。
- 默认视觉焦点应落在当前选中的命令项上。

### 5.1.4 右侧详情规则

- 右侧不是“信息垃圾桶”。
- 第一屏只能有一个主信息块。
- 详情区必须先回答：这个命令是什么、做什么、如何执行。
- 统计信息只能作为辅助，不要抢主叙事。

### 5.1.5 Footer 规则

- Footer 用于说明当前可执行的键盘动作。
- 不要放太多状态文本。
- 快捷键提示应短小、准确、重复性低。

## 5.2 Plugins 页面

### 5.2.1 页面目标

让用户理解：

- 当前有哪些官方能力
- 它们有什么权限
- 是否启用
- 后续可以扩展到哪里

### 5.2.2 推荐结构

- 顶部说明：官方工具、权限、扩展路线
- 中部插件卡片网格
- 底部或侧部权限摘要 / 说明区

### 5.2.3 卡片规则

- 卡片中只保留插件名、简介、状态、命令数、权限概况。
- 避免堆太多说明文字。
- 视觉上更像“catalog item”而不是“设置条目”。

## 5.3 Settings 页面

### 5.3.1 页面目标

让用户快速调整基础行为，不做复杂配置中心。

### 5.3.2 推荐结构

- 顶部：当前环境状态
- 中部：Appearance / Invocation / Desktop Integration 三组
- 底部：补充说明、未来配置预留

### 5.3.3 交互规则

- 能切换的就直接切换
- 能预览的尽量即时预览
- 不要在 V0.1 引入复杂表单流程

## 6. 工具视图规范

当前 JSON / Base64 / Timestamp / UUID 都属于“内置工具视图”，它们必须遵守同一种工具页规范。

### 6.1 工具页结构

```text
Tool Header
- Eyebrow
- Title
- Description
- Type tags

Tool Main Area
- Input / Output / Preview

Tool Actions
- Copy / Generate / Run

Tool Notes
- Detail / metadata / tips
```

### 6.2 工具页要求

- Header 应像正式产品里的工具面板，不是简单 `h2`
- 输入输出区域要明确主次
- `CodeBlock` 应承载主要结果展示
- 辅助说明统一走 `Detail`
- 每个工具页视觉结构一致，但内容布局可以略有差异

### 6.3 不允许的写法

- 不要只放几个 `label + input + button`
- 不要直接裸用浏览器默认表单布局
- 不要每个工具页都像完全不同的站点

---

## 7. 视觉方向补充规范

## 7.1 层级原则

全局最多只允许三层视觉重心：

1. 当前主操作区
2. 当前选中项 / 当前工具结果
3. 辅助说明区

其他元素必须退后。

## 7.2 渐变使用原则

- 渐变只能服务于品牌或焦点
- 不允许大面积滥用
- Hero 卡片可用轻度 accent glow
- 普通卡片不需要都带渐变

## 7.3 圆角原则

- Window: `18px`
- Panel: `16px`
- Item: `12px`
- Control: `10px`

不应再引入新的随意圆角体系。

## 7.4 边框原则

- 边框主要用于结构分隔，不用于装饰
- 同一屏不要出现太多等权边框盒子
- 如果一个区域已经靠背景对比形成层次，就不一定再需要重边框

## 7.5 阴影原则

- Window shadow 强
- Panel shadow 中
- 普通内部卡片尽量弱或不用

---

## 8. 文案规范

当前文案需要统一，不再允许：

- 乱码
- 中英文混乱无规则
- 过度工程化命名直接暴露给用户

### 8.1 V0.1 文案策略

- UI 先统一英文，或统一中文，不能混用失控
- 如果选择英文：
  - Product / section / action 用英文
  - 内部 id / plugin id 不直接暴露给用户作为主文案
- 如果选择中文：
  - 技术术语允许保留少量英文

建议：

> 当前阶段优先统一英文界面文案，避免字体混排失控。

---

## 9. 组件体系开发要求

当前 `src/ui/` 是正确方向，后续必须坚持。

### 9.1 所有新页面优先使用 `src/ui`

禁止：

- 新页面再回到旧 `src/components/*`
- 页面里重新写一套不受控样式
- 直接用页面私有样式绕过组件层

### 9.2 组件分层

- `src/ui/`: 通用基础 UI 组件
- `src/pages/`: 页面结构与业务编排
- `src/styles/`: token 与全局约束
- `src/builtin-plugins/`: 工具视图内容实现

### 9.3 需要继续补齐的组件

V0.1 应继续补齐：

- `Markdown`
- `Toast`
- `ActionPanel`
- `Action`
- `List.Section`

这些组件补齐后，整个产品才会更完整。

---

## 10. 现阶段代码整理要求

开发前先明确以下整理目标：

### 10.1 清理旧 UI 体系

逐步废弃：

- `src/components/CommandInput.tsx`
- `src/components/CommandList.tsx`
- `src/components/CommandListItem.tsx`
- `src/components/WindowHeader.tsx`

它们已经不应该继续主导项目。

### 10.2 清理历史样式残留

目标：

- `src/styles/index.css` 只保留全局布局级样式
- 页面私有结构尽量放入对应页面 CSS
- 工具页共用规则集中在 `tool-views.css`

### 10.3 减少“演示型信息块”

当前很多页面会出现以下问题：

- 为了显得完整而堆卡片
- 为了显得技术而堆统计
- 为了显得高级而堆标签

后续开发必须更克制。

## 11. 分阶段开发计划

## Phase 1：文档与视觉方向锁定

目标：

- 写清本文件
- 不再继续随机改页面
- 明确页面级标准

完成标准：

- 有统一产品目标
- 有统一视觉方向
- 有统一页面结构规则

## Phase 2：应用级页面骨架重做

目标：

- Launcher / Plugins / Settings 全部统一骨架
- 完成标题、导航、页脚、容器规范

完成标准：

- 三页像同一个产品
- 页面 header / footer / spacing 统一

## Phase 3：Launcher 深化

目标：

- 把 Launcher 做成真正的主入口
- 优化搜索区、列表区、详情区、工具视图切换体验

完成标准：

- 第一眼知道这是启动器
- 键盘交互合理
- 信息优先级明确

## Phase 4：工具视图统一重做

目标：

- JSON / Base64 / Timestamp / UUID 全部统一工具面板风格
- 使用 `CodeBlock` / `Detail` / `ErrorState`

完成标准：

- 工具页不再像 demo
- 结果展示稳定可读

## Phase 5：组件补全

目标：

- 完成 `Markdown` / `Toast` / `ActionPanel` / `Action`
- 建立更完整的 UI SDK

完成标准：

- 设计文档主要组件基本齐全

## Phase 6：代码清理与一致性收口

目标：

- 删除旧组件残留
- 减少重复样式
- 页面结构与组件层关系清晰

完成标准：

- 没有两套 UI 长期并存
- 后续继续开发不再混乱

---

## 12. 每阶段验收标准

### 12.1 视觉验收

- 页面像同一个产品
- 主次分明
- 没有明显 demo 感
- 没有大量无意义装饰

### 12.2 工程验收

- `pnpm typecheck` 通过
- `pnpm build` 通过
- 页面开发优先走 `src/ui`
- 样式遵守 CSS Variables

### 12.3 交互验收

- 键盘操作顺滑
- 焦点状态明确
- 打开工具视图不割裂
- 空状态与错误状态可读

---

## 13. 下一步开发建议

在本文件落地后，后续开发顺序建议固定为：

1. 先清理页面层级与旧组件残留
2. 再重做 Launcher 的视觉优先级
3. 再补 `ActionPanel / Toast / Markdown`
4. 最后统一收口 Plugins / Settings / Tool Views 的细节

### 明确禁止

- 不要再直接“先写页面看看效果”
- 不要继续边做边拼卡片
- 不要在没有页面规范的情况下继续加功能

---

## 14. 当前执行结论

从现在开始，QuickBox 后续开发应遵守以下原则：

> 先按本文件定义页面结构和产品气质，再开发页面和组件；  
> 先让它像一个正式产品，再让它功能继续增加。

本文件写完之前，继续堆 UI 代码会让项目越改越乱。  
本文件写完之后，所有开发应围绕“统一产品感”推进，而不是只追求“页面不空”。
