# QuickBox 项目发展规划

规划日期：2026-10-14。基于当前工作区代码（包含尚未提交的页面改造）与已有项目文档。

本文是后续开发建议，不代表功能已经实现或排期已经承诺。本次进行了代码和文档静态检查，未启动桌面应用做视觉验收，也未运行构建和性能测试。工期按一位熟悉项目的开发者持续投入估算，应在第一阶段结束后调整。

## 1. 产品定位与发展主线

建议定位：**Windows 优先、本地优先、键盘驱动的开发者工作台**。

优先服务经常处理 JSON、编码、时间、接口数据和本地开发环境的前后端开发者；其次覆盖测试和运维人员。目标用户与使用频率仍需通过实际试用验证。

核心价值是缩短一次小任务从出现到完成的时间：呼出 → 找到动作 → 带入数据 → 得到结果 → 返回原来的工作。

未来发展的三条主线：

1. **入口效率**：搜索可靠、键盘流畅、常用动作触手可及。
2. **工具联动**：统一输入输出，让已有工具可以连续处理同一份数据。
3. **按需扩展**：轻量核心承载高频能力，较重的系统、OCR 和 AI 能力按需增加。

当前阶段保留 Launcher、Plugins、Settings 三个一级入口。沿用此次改造的分类、常用区、列表和工具工作区结构；只有具体任务验证出问题时，才调整页面结构。

## 2. 现状判断

| 方面 | 当前代码证据 | 对后续规划的含义 |
| --- | --- | --- |
| 工具基础 | `builtin-loader.ts` 注册 18 个内置插件，其中三个为多工具集合 | 已有较广覆盖，应优先提高完成任务的效率 |
| 页面改造 | Launcher 已拆出分类、常用工具、工具行和工作区组件，窗口改为 1180×740 | 可以在现有页面上深化交互；小屏和高 DPI 适配仍需真机验证 |
| 搜索 | 支持精确、前缀、包含匹配及使用频率加权 | 还不是完整的容错模糊搜索；应先修正确性，再增加别名与拼音 |
| 搜索缺陷 | `searchCommands` 在过滤前叠加使用分，未匹配但用过的命令可能进入结果 | 列为第一批修复：先判断文本命中，再在命中集合内排序 |
| 数据入口 | `launcher-clipboard.ts` 已有识别规则，但当前代码未找到调用点 | 可以接入推荐入口，但识别规则还需有效性校验 |
| 数据传递 | `openView(viewId, params)` 已有参数通道；JSON 工具仍使用自身初始值 | 统一参数契约即可从少数工具开始打通，无需重写注册体系 |
| 剪贴板历史 | SQLite 保存最多 100 条，监听位于工具组件，打开期间每 2 秒轮询 | 当前不是独立后台服务；后台记录需明确开关、生命周期与保留规则 |
| 偏好保存 | 常用工具存 localStorage；配置、插件状态、使用记录存 SQLite | 统一持久化入口后才能可靠备份、恢复和迁移 |
| 工具代码 | 三个集合型 View 文件分别超过 600、1000、2000 个非空行 | 按工具逐步拆分，降低修改影响面，并为按需加载做准备 |
| 插件体系 | 已有 metadata、命令、视图和启停状态；入口为静态导入 | 当前是内置工具模块化，尚不是可安装的外部插件平台 |
| 权限 | 有权限声明类型，系统 API 通过 Tauri command 调用 | 声明不等同运行时鉴权；外部插件开放前需实现可信权限边界 |
| 数据迁移 | 创建了 `schema_migrations`，当前迁移函数未按版本执行和记录迁移 | 新增持久化模型前应补齐版本迁移与旧数据兼容 |
| 交付 | 有 Windows/Linux Release 工作流，未发现常规测试脚本及测试文件 | 补核心逻辑回归与 PR 检查，桌面能力需真实桌面验收 |
| 文档 | README 标注 0.1.2，三处应用配置为 1.0.0；旧需求包含已实现工具 | 以当前代码校准功能清单与版本，避免重复开发 |

补充交互检查项：Launcher 的全局 Tab 处理会拦截默认行为，应验证工具表单内 Tab/Shift+Tab 是否能正常移动焦点；搜索变化会关闭工具视图，应配合草稿恢复防止输入丢失。以上来自静态路径检查，需在桌面环境复现验收。

## 3. 最值得形成的差异

### 3.1 内容驱动入口

典型流程：用户复制 JSON，呼出 QuickBox，选择“用 JSON 工具处理”，内容直接进入输入区，处理后复制结果。

第一批仅覆盖 JSON、时间戳、URL、JWT、CIDR。推荐动作可忽略，普通搜索始终可用。JWT 解码结果明确区分“已解析”和“签名已验证”。

识别与执行解耦：识别只产生候选动作，用户触发后才写入工具输入。剪贴板识别与历史记录分别设置开关；开启识别不意味着自动保存原文。

### 3.2 结果可以继续处理

先做三条固定链路：

- JSON → 格式化 → TypeScript 类型 / JSON Schema。
- URL 解码 → Query 参数查看与编辑。
- 文本清洗 → 去重 → CSV / JSON 转换。

通过结果区“发送到工具”动作完成。先解决两个工具之间的数据交接，再基于实际重复场景考虑可保存的步骤组合。

### 3.3 桌面能力带来的价值

优先深化已经实现的端口处理、文件内容搜索、文件哈希和批量重命名。它们可与本地项目直接结合，能发挥 Rust 系统层的优势。

端口处理展示进程身份与操作结果；文件操作提供预览、冲突信息与结果报告。现有批量重命名已有执行 API，规划应围绕可靠性补齐，不重复当作全新功能开发。

## 4. 分阶段路线

版本号暂按当前配置的 1.0.0 往后命名，实际发布号应结合已有标签确认。

| 阶段 | 建议规模 | 主要交付 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| M0 / 1.0.x：稳定基线 | 1–2 周 | 搜索修复、键盘与焦点、异常隔离、文档校准、核心回归 | 主要任务可完成，已知阻断问题清零，桌面检查通过 |
| M1 / 1.1：数据流转 | 2–3 周 | 统一输入输出、剪贴板推荐、内存草稿、三条工具链路 | 数据能准确带入和传递，切换不丢输入，错误不传作结果 |
| M2 / 1.2：个人工作台 | 2–3 周 | 本地片段、工具预设、偏好备份恢复 | 常用内容可找回，导入导出与升级不丢数据 |
| M3 / 1.3：桌面效率与交付 | 3–4 周 | 现有系统工具深化、按需加载、发布与升级体验 | 有实测性能基线，Windows 安装/升级/恢复链路验证完成 |
| M4 / 后续大版本：可选扩展 | 先做技术验证，再估时 | 官方扩展包闭环，再考虑第三方和 OCR/AI | 安装、校验、权限、卸载、失败恢复与兼容性机制齐备 |

M0–M3 合计约 8–12 个开发周，包含基本验证，不包含开放插件生态。第一轮只锁定 M0 和 M1；若一阶段延期，后续顺延，不通过省略验证来追赶版本号。

### M0：先稳定此次改造

交付内容：

- 修复搜索未命中仍因使用分进入结果的问题，建立覆盖中英文、空查询、无匹配和历史权重的用例。
- 明确 Esc 的逐层退出、Enter 的当前动作、Tab 的表单移动、全局快捷键与中文输入法组合输入边界。
- 常用区满 8 个时明确替换行为；支持调整顺序，并保证 Alt+数字与展示位置一致。
- 工具视图增加错误边界，命令执行统一处理失败；单个工具报错后仍可返回搜索。
- 先测代表性工具的布局：JSON、端口、Diff、剪贴板、设置、插件页，覆盖亮暗主题、最小窗口与 125%/150% 缩放。
- 核对 README、实际功能、应用版本与历史规划，给旧需求标注已实现/部分实现/待验证。
- 加入 PR 级 typecheck、build、Rust check 和关键逻辑测试；桌面验收另列清单。

验收示例：使用过 JSON 工具后输入完全无关的词，列表为空；工具输入框内 Tab 可以移动到下一个控件；连续呼出隐藏 30 次，搜索仍可获得焦点；一个工具异常不导致整个应用不可用。

### M1：把工具接起来

交付内容：

- 定义 `ToolInput`、`ToolResult` 和 `ToolAction` 的最小契约，包含数据类型、内容、来源和敏感标记。
- 保留现有 `openView`，通过适配器兼容旧工具，首批迁移 JSON、时间戳、URL、JWT、CIDR。
- 首次接入剪贴板识别时保留现有长度限制，补 CIDR、时间戳等有效性检查，避免仅凭正则认定有效。
- 草稿先保留在内存，关闭应用后是否恢复由后续明确设置控制；密钥等敏感输入默认不落盘。
- 统一结果操作：复制、清空、发送到兼容工具；失败结果单独表达，禁止当成功文本继续流转。
- 实现本规划列出的三条工具链路；涉及文件写入或进程终止的动作不自动连跑。

验收示例：复制 JSON → 呼出 → 选择推荐 → 格式化 → 发送到 TypeScript 工具 → 复制类型，全程不需要手工搬运中间文本；切换搜索后返回，原工具草稿仍在；无效数据能定位错误。

### M2：沉淀个人习惯

交付内容：

- 本地片段管理：标题、内容、语言、标签、搜索、复制、导入导出；首版不引入团队协作。
- 工具预设：保存常用选项，例如时间戳单位、JSON 缩进、命名转换模式。
- 常用工具统一进入配置存储服务，并迁移旧 localStorage 数据；确认写入成功后才标记迁移完成。
- 备份包含版本信息与校验，导入前预览冲突，失败时保留原有数据。默认不导出剪贴板历史、密钥和敏感草稿。
- 剪贴板历史如果升级为后台能力，应移到应用服务层或 Rust，提供明确启停和过期清理，避免依赖页面是否挂载。

验收示例：新安装环境导入备份后常用区和预设一致；重复导入不会重复创建数据；损坏文件不会覆盖现有配置；迁移失败后重启仍可重试。

### M3：深化桌面体验

优先完成已有能力：文件搜索增加取消、进度和排除目录；批量重命名增加批次预览、重名冲突处理与结果清单；端口工具结合现有使用记录形成常用端口入口。回退功能必须说明适用条件，不能承诺在文件被外部修改后仍能无条件撤销。

新增能力只选一项试点，建议候选为“本地网络信息/DNS 查询”或“轻量 HTTP 请求”。由试用反馈决定，不同时扩成完整网络客户端。

工程上拆分大型工具集合，分离轻量元数据与重型视图，按需加载 Diff、二维码等模块。大文本和目录扫描补尺寸限制、取消能力和明确反馈，具体转 Worker 或 Rust 以测量结果决定。

发布先补版本信息、更新说明、检查更新入口和下载引导，再接入自动更新。Tauri 更新流程涉及签名和更新元数据，应作为完整发布链路实现，而不是单独增加一个按钮。参见 [Tauri Updater 官方文档](https://v2.tauri.app/plugin/updater/)。

### M4：先验证官方扩展包

现有市场方案保留为需求素材，但调整执行顺序：先做真实可用的官方扩展包，再完善发现与展示页面。未能下载或运行的条目不得显示“安装成功”。

最小闭环：清单 → 兼容性检查 → 下载 → 校验 → 安装 → 配置 → 启用 → 更新 → 卸载 → 失败恢复。

插件清单至少声明插件/API 版本、平台、权限、网络需求、资源体积、依赖和入口。先区分随应用发布的内置模块、可选官方资源/进程与第三方代码，分别设计运行边界。

权限必须在可信宿主边界强制执行。同一 WebView 中传入一个 `pluginId` 不能证明调用者身份；Tauri capability 主要针对 window/webview，不能把前端 metadata 当成每个 React 插件的安全沙箱。参见 [Tauri Capabilities 官方文档](https://v2.tauri.app/security/capabilities/)。

先选择一个确有需求的官方可选包验证生命周期，再考虑 OCR；AI 能力作为显式网络动作，需要用户配置服务与凭证，并清楚展示将发送的数据。开放第三方插件前，单独完成运行隔离、签名、权限与兼容性验证。

## 5. 工程演进原则

### 保留现有技术栈，逐步收敛边界

继续使用 React + TypeScript + Zustand + Tauri/Rust + SQLite，按实际瓶颈改造。

| 层级 | 建议职责 | 首批落点 |
| --- | --- | --- |
| 页面 | 导航、布局、用户交互编排 | `src/pages/LauncherPage.tsx`、`src/pages/launcher/` |
| 命令核心 | 搜索、调用上下文、执行状态与错误 | `src/core/command/` |
| 工具协议 | 输入输出、可用动作、草稿、工具交接 | 新增小型 `src/core/tool/`，按 M1 需要实现 |
| 工具实现 | 纯转换逻辑、参数验证、视图 | `src/builtin-plugins/`，集合文件逐个拆分 |
| 系统服务 | 剪贴板、文件、进程、权限和长期任务 | `src/api/`、`src-tauri/src/commands/` |
| 持久化 | 配置、迁移、片段、预设、备份恢复 | `src-tauri/src/storage/` |

类别、图标、别名应逐步下沉到命令元数据，保留兼容默认值，避免每新增工具都修改 Launcher 的硬编码映射。不要为了未来插件市场提前搭建庞大的通用框架。

### 数据设计约束

遵守项目 AGENTS 指令：禁止物理外键、无意义函数、存储过程、视图和触发器；建表、加字段必须补充 SQL 注释及数据库内的表/字段说明。

当前使用 SQLite，其建表语法没有 MySQL 式 `COMMENT` 子句。建议在迁移 SQL 中写明用途，并用数据库内的元数据说明表持久保存表/字段注释，配合数据字典文档满足注释可查询要求；这是后续实施方案，本次不创建表。语法依据见 [SQLite CREATE TABLE 文档](https://www.sqlite.org/lang_createtable.html)。

实体关系由应用事务维护，必要处使用唯一约束和索引。M2 可能需要片段、预设及偏好模型，M4 才增加插件安装记录；不提前创建空业务表。

迁移应具备版本记录、幂等检查、事务和失败恢复，升级前先验证旧数据库样本。备份恢复包含数据库与配置格式版本，避免直接用新结构覆盖旧库。

## 6. 首轮可以直接开发的任务

| 顺序 | 任务 | 代码落点 | 完成标准 |
| --- | --- | --- | --- |

| 5 | 输入输出协议及草稿试点 | `command-types.ts`、`plugin-types.ts`、JSON 工具 | JSON 能接收传入内容，切换后恢复，错误与结果分离 |
| 6 | 剪贴板推荐试点 | `launcher-clipboard.ts`、Launcher | JSON/时间戳端到端可用，关闭推荐后停止识别 |
| 7 | JSON → TypeScript / Schema | 对应工具及统一结果动作 | 内容与选项可验证地传递，无手工复制中间数据 |

第 1–4 项构成首个稳定迭代；第 5–7 项构成首个可感知的新能力迭代。第 8 项是 M2 的前置条件。

## 7. 怎么判断规划是否有效

首要指标是固定任务是否更快完成，以及用户是否愿意持续使用。现有 `runCount` 在命令打开后记录，只能代表使用入口，不能直接视为任务完成。

先使用不含原文的本地诊断和人工任务记录，无需先建设在线统计系统。

| 验证内容 | 第一轮做法 | 建议目标（待基线校准） |
| --- | --- | --- |
| 找到工具 | 固定 30 条中英文与别名查询，核对预期结果 | 高频查询目标工具进入前 3 项；不相关查询不返回历史噪音 |
| 完成任务 | 固定 10 个任务，记录唤起到复制结果的步骤和耗时 | M1 相比 M0 的中位耗时下降约 30% |
| 响应速度 | 固定 Windows 机器、发布构建，预热后重复测量 | 热唤起可输入 p95 ≤ 200ms；500 条命令检索 p95 ≤ 50ms |
| 数据可靠性 | 旧库升级、重启、导入冲突、损坏备份验证 | 核心配置和用户片段零静默丢失 |
| 常驻成本 | 记录后台空闲 CPU、内存、包体与初次启动时间 | 后续版本的明显增长必须能解释，并能按需关闭重能力 |
| 真实价值 | 邀请 5–10 位目标用户试用两周，收集完成与放弃的任务 | 据重复使用的任务确定 M2/M3 范围，而非按工具数量排期 |

上述性能和效率数值是建议验收目标，不是当前实测结果。浏览器预览存在系统 API 模拟结果，不能替代桌面剪贴板、进程、文件、热键和安装升级验收。

## 8. 后续投入边界
